# Requirements Document

## Introduction

This document specifies the requirements for the Zedral platform database schema — a production-ready PostgreSQL 16 + TimescaleDB migration covering all operational modules for mid-market Indian steel manufacturers. The anchor pilot is Hero Steels Limited (Ludhiana), cold rolling strip operation with three CRS lines (CRS-1, CRS-2, CRS-3) at 180,000 MTPA combined capacity.

The schema spans eight module namespaces (`master`, `m1_demand`, `m3_capacity`, `m4_schedule`, `m5a_material`, `m6_dispatch`, `m7_performance`, `m8_energy`) plus the TimescaleDB extension setup. It must be deliverable as a single idempotent migration file that can be applied to a fresh PostgreSQL 16 instance with TimescaleDB installed.

## Glossary

- **CRS**: Cold Rolling Strip — the primary production process at Hero Steels
- **WO**: Work Order — a production order, typically sourced from SAP PP
- **SO**: Sales Order — a customer order from SAP SD
- **WC / Work Centre**: A production line (e.g., CRS-1, CRS-2, CRS-3)
- **Routing**: The sequence of operations required to produce a material
- **Changeover Matrix**: A lookup table mapping (from-grade, from-gauge, from-width) → (to-grade, to-gauge, to-width) to a setup time in minutes
- **OEE**: Overall Equipment Effectiveness = Availability × Performance × Quality
- **SEC**: Specific Energy Consumption — kWh per tonne of output
- **RCCP**: Rough-Cut Capacity Planning — coarse feasibility check before detailed scheduling
- **APS**: Advanced Planning and Scheduling — the CP-SAT-based finite scheduler (M4)
- **HR Coil**: Hot-Rolled coil — the raw material input to cold rolling
- **CR Coil**: Cold-Rolled coil — the output of the rolling process
- **Hypertable**: A TimescaleDB table automatically partitioned by time
- **UUID-v7**: Time-ordered UUID variant used for event IDs
- **HMAC**: Hash-based Message Authentication Code — used to sign floor events
- **BRSR**: Business Responsibility and Sustainability Report — Indian regulatory ESG filing
- **CEA**: Central Electricity Authority — publishes India's grid emission factor
- **DISCOM**: Distribution Company — the electricity utility (PSPCL for Hero Steels)
- **SAP_Sync_Worker**: The shared service that pulls data from SAP ECC via OData
- **Redpanda**: The Kafka-API-compatible event backbone used by Zedral
- **TimescaleDB**: PostgreSQL extension for time-series data with automatic partitioning
- **Materialised_View**: A module table rebuilt from the event log; not a PostgreSQL MATERIALIZED VIEW object
- **Stoppage_Code**: A catalogue entry classifying a production stoppage (16 codes for Hero Steels)
- **Defect_Code**: A catalogue entry classifying a quality reject (45 codes for Hero Steels)
- **Roll**: A work roll set used in the 6-HI cold rolling mill
- **Pass**: One rolling pass through the mill; cold rolling requires 3–6 passes per coil
- **Grind Cycle**: Periodic regrinding of rolls to restore surface quality
- **Emission_Factor**: kgCO₂e per kWh — sourced from CEA grid factor for Scope 2 calculation
- **Line_Share**: Historical proportion of production allocated to each eligible CRS line for a grade family
- **Dispatch_List**: A shift-level ordered list of jobs for one CRS line
- **Execution_Event**: An append-only, HMAC-signed record of a shop-floor fact
- **Shift_Handover**: The structured transfer of state between outgoing and incoming shift operators
- **Production_Pass**: One rolling pass record under a dispatch item (v0.2 multi-pass model)
- **Snapshot**: A point-in-time computed record (capacity, KPI, SEC) stored for historical querying
- **Watermark**: The last-synced SAP timestamp used to drive incremental pulls

## Requirements

### Requirement 1: Database Foundation and Cross-Cutting Conventions

**User Story:** As a platform engineer, I want a consistent, well-structured PostgreSQL database foundation, so that all modules share the same conventions and the schema is maintainable across the platform's lifetime.

#### Acceptance Criteria

1. THE Migration_Script SHALL create all required PostgreSQL schemas in a single idempotent file: `master`, `m1_demand`, `m3_capacity`, `m4_schedule`, `m5a_material`, `m6_dispatch`, `m7_performance`, `m8_energy`.
2. THE Migration_Script SHALL enable the `timescaledb` extension before creating any hypertables.
3. THE Migration_Script SHALL enable the `pgcrypto` extension to support `gen_random_uuid()`.
4. WHEN a table is created, THE Schema SHALL include `created_at TIMESTAMPTZ DEFAULT now()` and `updated_at TIMESTAMPTZ DEFAULT now()` audit columns on every non-hypertable, non-append-only table.
5. THE Schema SHALL use `TEXT` natural keys (not surrogate integers) for all cross-module foreign key references where the planning documents specify natural keys (e.g., `wo_id`, `wc_id`, `material_code`, `coil_id`).
6. THE Schema SHALL use `JSONB` for all flexible or evolving fields documented as `raw_sap_payload`, `payload`, `score_components`, `input_snapshot`, `assumptions`, `action_details`, and similar.
7. THE Schema SHALL use `UUID` (via `gen_random_uuid()`) as the primary key type for all entity tables that are not natural-key-primary or BIGSERIAL time-series tables.
8. THE Schema SHALL use `BIGSERIAL` primary keys for high-volume append-only tables (`kpi_snapshots`, `meter_readings`, `interval_energy`, `sec_snapshots`, `coil_stage_history`, `priority_score_history`, `validation_errors`).
9. WHEN an event ID column is defined, THE Schema SHALL use `UUID` typed as UUID-v7 (time-ordered) with a comment noting the UUID-v7 requirement.
10. THE Migration_Script SHALL be re-runnable with `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and `CREATE SCHEMA IF NOT EXISTS` guards throughout.
11. THE Schema SHALL include inline SQL comments on every table and on columns whose purpose is non-obvious, documenting status machine values, design rationale, and cross-module references.

12. THE Schema SHALL create `master.defect_codes` with columns: `code_id TEXT PRIMARY KEY`, `code TEXT NOT NULL UNIQUE`, `description TEXT NOT NULL`, `defect_category TEXT NOT NULL`, `severity TEXT`, `is_active BOOLEAN DEFAULT TRUE`, `sort_order INTEGER`, `created_at`, `updated_at`.
13. THE Schema SHALL create `master.emission_factors` with columns: `factor_id TEXT PRIMARY KEY`, `source TEXT NOT NULL`, `fiscal_year TEXT NOT NULL`, `scope CHAR(1) NOT NULL`, `kg_co2e_per_kwh NUMERIC(8,5) NOT NULL`, `valid_from DATE NOT NULL`, `valid_to DATE`, `citation TEXT`, `created_at`, `updated_at`.

19. THE Schema SHALL seed `master.defect_codes` with representative defect codes covering the major defect categories for cold rolling (edge crack, surface scratch, thickness variation, shape defect, etc.).
20. THE Schema SHALL create indexes on `master.changeover_matrix (wc_id, grade_from, grade_to, gauge_step, width_step)` and `master.resource_calendars (wc_id, calendar_date)`.

### Requirement 10: Migration File Structure and Idempotency

**User Story:** As a platform engineer deploying to a fresh PostgreSQL 16 instance, I want a single well-structured migration file, so that the entire schema can be applied in one command without errors on a clean database or on re-application.

#### Acceptance Criteria

1. THE Migration_Script SHALL be a single `.sql` file located at `infra/postgres/init/001_zedral_schema.sql`.
2. THE Migration_Script SHALL begin with a header comment documenting: version, date, description, and the list of schemas created.
3. THE Migration_Script SHALL use `CREATE SCHEMA IF NOT EXISTS` for all eight schemas.
4. THE Migration_Script SHALL use `CREATE TABLE IF NOT EXISTS` for all tables.
5. THE Migration_Script SHALL use `CREATE INDEX IF NOT EXISTS` for all indexes.
6. THE Migration_Script SHALL execute `CREATE EXTENSION IF NOT EXISTS timescaledb CASCADE` and `CREATE EXTENSION IF NOT EXISTS pgcrypto` before any table creation.
7. THE Migration_Script SHALL wrap all `create_hypertable` calls in a `DO $$ BEGIN ... EXCEPTION WHEN others THEN NULL; END $$` block to make them idempotent on re-run.
8. THE Migration_Script SHALL use `INSERT ... ON CONFLICT DO NOTHING` for all seed data rows.
9. THE Migration_Script SHALL be organised in sections in this order: extensions, schemas, master schema tables + indexes + seed data, m1_demand, m3_capacity, m4_schedule, m5a_material, m6_dispatch, m7_performance, m8_energy.
10. WHEN the migration file is applied to a PostgreSQL 16 instance with TimescaleDB installed, THE Migration_Script SHALL complete without errors and produce all 8 schemas, all tables, all indexes, and all seed rows.
11. THE Migration_Script SHALL include a final `SELECT` statement that counts tables per schema as a smoke-test comment, documenting the expected table counts: master=14, m1_demand=7, m3_capacity=5, m4_schedule=7, m5a_material=8, m6_dispatch=12, m7_performance=9, m8_energy=8.
